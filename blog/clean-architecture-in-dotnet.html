Clean Architecture in .NET

Most "Clean Architecture" samples you find online are folder naming with a diagram attached. The idea is smaller than the ceremony — and easier to test than the ceremony suggests.

  • Nov 8, 2026
  • 8 min read
  • Development

I have rebuilt NexaPOS once because the domain logic was welded to Entity Framework. The second time I kept one rule and skipped most of the ceremony: dependencies point inward. That rule is the architecture. The rest is where you put files.

The only rule that matters

Inner layers must not know about outer layers. Your business rules should compile without a reference to SQL Server, ASP.NET Core, or the mail provider. If they do, the architecture is a diagram, not a constraint.

A quick check before you add anything else: open the domain project's .csproj. It should reference nothing but the framework. The moment Microsoft.EntityFrameworkCore shows up there, the database has moved into the middle of your business.

Four projects, four jobs

  • Domain — entities, value objects, invariants. No I/O, no attributes from frameworks, no base classes.
  • Application — use cases, ports (interfaces), validation. This is where a request becomes a decision.
  • Infrastructure — EF Core, HTTP clients, file storage, e-mail. The messy, replaceable edge.
  • Api — routing, auth, serialisation, status codes. Thin on purpose.
src/
├── NexaPOS.Domain/          # no references
├── NexaPOS.Application/     # → Domain
├── NexaPOS.Infrastructure/  # → Application
└── NexaPOS.Api/             # → Application, Infrastructure (wiring only)

A concrete example

Say checkout needs the current time — for a discount window. Do not call DateTime.Now inside the domain. Declare the need as a port: 

// Application/Abstractions/IClock.cs
public interface IClock
{
    DateTime UtcNow { get; }
}

// Application/Sales/CheckoutHandler.cs
public sealed class CheckoutHandler
{
    private readonly IClock _clock;
    private readonly ISaleRepository _sales;

    public CheckoutHandler(IClock clock, ISaleRepository sales)
    {
        _clock = clock;
        _sales = sales;
    }

    public async Task<SaleResult> HandleAsync(Checkout command, CancellationToken ct)
    {
        var sale = Sale.Create(command.CartId, _clock.UtcNow);
        sale.ApplyDiscounts(command.CouponCode);

        await _sales.SaveAsync(sale, ct);
        return SaleResult.From(sale);
    }
}

Infrastructure supplies SystemClock and an EF-backed repository. Tests supply a fixed clock and an in-memory list. Nothing in the use case knows either exists, which is the whole point.

Where people get it wrong

  • One interface per repository method. If every query needs its own port, you have moved SQL into the application layer with extra typing.
  • Mapping three times. Entity → DTO → view model → JSON. Two of those are usually the same object.
  • Domain services that do everything. A 700-line SaleService is not cleaner than a 700-line controller. It is the same code in a different folder.
  • Skipping the inner layers. The API project calls EF Core directly "for now". Three months later the "for now" has endpoints nobody can test.

The measure of the architecture is how much of it you can run in a test project with no database and no web server. Everything else is taste.

When it is overkill

For a six-table internal tool with one client, four projects and a mediator pipeline will cost you more than they save. I still keep the domain free of EF Core, but I skip the abstractions until there is a second caller. Vertical slices — one folder per feature, handler next to its request — give you most of the isolation with a third of the files.

Start with the rule, not the tree. When the tree starts earning its keep — when you add a second delivery mechanism, or your tests need a fake database — split it then. Refactoring toward Clean Architecture is cheap. Explaining why you need eleven projects for a CRUD form is not.
