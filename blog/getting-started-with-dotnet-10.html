Getting Started with .NET 10

.NET 10 is an LTS release, which means the interesting part is not the demo — it is what survives three years of maintenance. Here is what I adopt on day one and what I leave alone.

  • Nov 3, 2026
  • 6 min read
  • Tools

Every release announcement lists twenty features. Most of them will not change how you work. .NET 10 has three that did for me: single-file programs, C# 14's smaller ergonomics, and validation that finally lives in minimal APIs instead of a controller.

Install without wrecking the old SDK

Use global.json so the repo pins its SDK version and CI stops drifting underneath you: 

dotnet new globaljson --sdk-version 10.0.100 --roll-forward latestFeature

# verify
dotnet --list-sdks

latestFeature lets patch releases through without allowing a major jump. That is the setting I want on a project that will be patched for three years.

File-based apps: the end of scratch projects

dotnet run app.cs compiles and runs a single file with directives for packages. For a benchmark, a migration script, or a throwaway API test, this replaces the whole "create a console project in a temp folder" ritual: 

#:package Dapper@2.1.66
#:property PublishAot=false

using Dapper;

using var db = new Microsoft.Data.SqlClient.SqlConnection(args[0]);
var rows = db.Query("select top 5 * from Sales order by Total desc");

foreach (var row in rows)
    Console.WriteLine(row);

It is not a replacement for a real project — no test runner, awkward multi-file growth — but for the 30-line programs I used to paste into a scratch file and forget, it is exactly right.

C# 14, in the order I noticed it

  • Extension members. Extension properties and static extension blocks mean fewer static class helpers that exist only to hold one method.
  • field keyword. Property accessors can touch the backing field without you declaring one. Good for validation-on-set.
  • Null-conditional assignment. user?.Name = "x"; now compiles. Small, but it removes a surprising number of if blocks.
  • Partial constructors and events. Source generators get cleaner; application code mostly does not care.

Validation in minimal APIs

In ASP.NET Core 10, validation attributes on minimal API parameters are enforced by the framework, and the failure result is a proper 400 with a problem-details body: 

app.MapPost("/sales", (SaleRequest request) =>
{
    // request is already validated when this runs
    return Results.Created($"/sales/{request.Id}", request);
});

I still keep domain invariants in the domain. This layer only rejects malformed input — which is precisely the job I used to write by hand in every endpoint.

What I would wait on

Native AOT keeps improving, but the moment your app touches dynamic serialisation, reflection-heavy libraries, or an ORM you did not audit, the trimming work eats the startup gains. For a small tool with a fixed JSON contract it is excellent. For a line-of-business API with EF Core at the centre, I would not spend the week yet.

The upgrade checklist

  • Pin the SDK with global.json; bump CI in the same commit.
  • Run dotnet list package --outdated and update the direct dependencies first.
  • Build with warnings as errors once, and read the nullable list — that is where regressions hide.
  • Exercise auth and billing paths by hand. They are the ones tests cover least and break most quietly.
  • Ship to staging for a week before production. LTS buys support; it does not buy you a free migration.

The honest summary: .NET 10 is a comfortable upgrade rather than a dramatic one. The file-based runner and minimal API validation are the two features that changed my daily loop. Everything else is polish on a platform that was already good.
